## 一、并行工具调用：一次提问，两个答案

### 现象

让模型一次返回 3 个工具调用，用户会收到 2 条最终答复，中间多花一次模型调用。全程没有任何报错，日志看起来一切正常。

### 为什么

两段各自都很合理的代码，凑在一起就错了。

LLM 插件忠实地把模型返回的每个工具调用都写成一条 `tool.call`：

```ts
for (const call of toolCalls) journal.append(TOOL_CALL, { ... })
```

流程插件则认为"工具有结果了就该让模型接着说"：

```ts
journal.subscribe(TOOL_RESULT, event => {
  journal.append(LLM_REQUEST, { purpose: 'agent', turnId: result.turnId })
})
```

3 条 `tool.call` 产生 3 条 `tool.result`，于是 3 次生成请求。流程插件的错误在于：它看到一条工具结果，就以为"这一轮的工具活儿都干完了"。**一条结果只是一个局部事实，"这一轮结束了"是个全局判断。**

值得注意的是上一版反而是安全的——它有一句 `throw new Error('parallel tool calls are not supported yet')`，不支持是显式的、会炸的。这一版把显式失败换成了静默的错误行为，是个退步。真实模型返回并行调用是常态，这个 bug 上真机必现。

### 改法里的一个陷阱

直觉的修法是"等所有 `tool.call` 都有 `tool.result` 再继续"。**这个条件不够。**

原因在内核的投递语义：追加的事件先全部进数组，然后才逐条投递。所以当第一条 `tool.result` 被投递时，第二、第三条**已经躺在 Journal 里了**。于是"没有未完成的调用"对三条结果**每一条都成立**，还是发三次。

正确的条件是两个：没有未完成的调用，**并且**当前这条结果是本轮最后追加的那条。

```ts
return outstanding.size === 0 && lastResult === result
```

这也是为什么测试里专门有一条"工具耗时不同也不影响 join"——用来钉死这个结论不依赖时序巧合。

### 通用规则

**局部事实不能直接当全局判断。** 一个插件想知道"这一类事情是不是都做完了"，唯一可靠的信息源是 Journal 的全量事实，而不是它手上这一条事件。

顺带这件事结清了上一份评审里挂着的 M2 悬案：**内核不需要 barrier、join、correlation 或 target。** `turnId` 加 `callId` 已经足够让插件自己 join 出来。

## 二、压缩水位线：被删掉的 `seq` 从后门溜回来了

### 现象

功能正常，测试全绿。问题在于压缩插件是这么记录"摘要覆盖到哪儿"的：

```ts
throughIndex: events.indexOf(event)
```

这个数组下标随后被写进 `history.checkpoint`——一条**持久事实**。

### 为什么

上一轮我们刻意从 `Event` 上删掉了 `seq`，理由是"一旦有它，插件会立刻拿它做水位线，从而在没有真实压力时提前固化 checkpoint 语义"。

现在的情况是：**压缩确实需要一个水位线，这个需求是真的。** 只是没有 `seq` 可用，插件就用 `indexOf` 自己造了一个，而且造得比内核 `seq` 更糟：

- 依赖引用相等，O(n) 扫全表；
- 这个下标只在**当前这一个内存 Journal 实例**里有意义。将来一旦有持久化裁剪、fork、replay，下标会**静默错位**，而不是报错。静默错位比崩溃可怕得多。

### 改法

水位线改成内容标识。每次生成本来就有唯一的 `requestId`，所以记 `throughRequestId`，需要位置时再扫描定位：

```ts
throughRequestId: result.requestId
```

扫描成本一样，但边界自描述、可跨持久化、trace 里一眼能看懂"这份摘要覆盖到哪次生成"。

### 通用规则

**指向事实的引用要用内容标识，不要用位置。** 位置会随着前缀变化而静默偏移；内容标识找不到时会明确报错。

这条也是一个**演进信号**，不是最终答案：如果 CASE2、CASE3 各自都需要一个水位线，那才是给内核加 `seq` 的正当证据。到那时它的语义（数组下标？全局单调 id？跨 session 怎么办？）会有三个真实约束来定义，而不是靠猜。现在先不加。

## 三、`llm.invoke`：把答案和演算过程一起存了

### 现象

Journal 体积对轮数呈**平方增长**。同一套流程实测：

| 轮数 | `llm.invoke` 字节 | 其余全部 | 占比 |
|---|---|---|---|
| 10 | 12 292 | 6 017 | 67.1% |
| 20 | 33 057 | 11 837 | 73.6% |
| 40 | 100 087 | 23 477 | 81.0% |

其余事件严格线性（每档刚好 2 倍），`llm.invoke` 是唯一的平方项，40 轮就吃掉 Journal 的 81%。

### 为什么

`llm.invoke` 把**materialize 好的完整 messages 数组**作为事件 payload 存了进去。第 N 次生成会把前 N 轮历史再抄一遍，所以是 O(n²)。

这里 mock 消息才几十字节。换成真实的 4k-token 上下文、跑几百轮，就是几百 MB，而且它是"事实"，将来持久化会全部落盘。

更关键的是：**这份 payload 是纯冗余。** 它本来就是 contextAssembler 从 Journal 推导出来的，那 Journal 当然能再推导一次。存一份完全可重算的东西，等于把演算过程当结论保存。

（Python 原型的 `ARCHITECTURE.md` 第 4 节明确避开过这个坑，还为此建了 `ContextViewStore`。这一版把结论丢了——这也说明"原型验证过的结论"如果不写进约束，就会在重写时丢失。）

### 改法，以及一个不明显的要求

`llm.invoke` 改成只带一份 **manifest**：摘要用哪个 checkpoint、尾部从哪到哪、本轮动态上下文是哪个 turn。真正的 messages 由一个纯函数 `projectMessages(events, invoke)` 现场重建。

不明显的要求是：**窗口的两端都必须钉住。**

只钉"从哪开始"是不够的——如果尾部是"到 Journal 末尾为止"，那么同一次调用在半小时后重放，尾部会变长，重建结果就不一样了。这样的 manifest 是不可信的。

所以尾部终点也用内容标识钉住：**到"正在服务的这次 invoke"之前为止**，通过 `requestId` 定位自己。于是同一次调用在任意时刻、对着任意更长的 Journal 重放，结果字节一致。

这条性质有专门的测试兜着：记录 provider 实际收到的 messages，跑完之后拿**最终**的 Journal 重建，`deepEqual` 比对。

### 效果

`llm.invoke` 从平方项变成严格线性（1 243 → 2 513 → 5 053，每档刚好 2 倍），占比稳定在 17% 左右，40 轮时 Journal 总量从 123.5KB 降到 28.8KB。

### 两个顺带的好处

**工具 schema 也不再重复。** 既然 manifest 里不能塞 messages，工具清单也不该每次都抄一遍。改成 `toolsPlugin` 在 `session.start` 追加一条 `tool.registry`，投影时从 Journal 读。这同时解决了上一份评审 5.1 节留的那个不一致（`system` 来自 Journal 而 `tools` 来自装配层配置），并且让动态工具发现变成一次普通的 Journal 读取。

**provider 变纯了。** 它现在收到的是一个 materialize 好的调用，而不是一个 Journal 事件，离"纯传输"更近了一步——这正是以后抽共享 OpenAI 客户端需要的那条缝。

### 通用规则

**可重算的东西不要当事实存。** Journal 存的应该是"发生了什么"和"怎么重建",不是"重建的结果"。

**任何"窗口"都要两端封闭。** 只封一端的窗口，含义会随时间漂移。

## 四、内容仲裁：`content.no_match` 名不副实

### 现象

功能正常——因为恰好只有一个内容生产者。

### 为什么

`content.no_match` 的真实含义是"**我这一个插件**没命中"，但流程插件把它当成"**没有任何 provider** 命中"来消费，直接转成一次 LLM 请求。

一旦装配表里出现第二个内容生产者（小模型分类器、缓存、更多规则包，也就是 Q01 第 7 点的原始诉求），每个不命中的插件都会追加一条 `content.no_match`，于是一次用户提问产生多次模型请求——**和第一节的并行扇出是同一个错误**，换了件外衣。如果两个都命中，则产生两条冲突输出而无人仲裁。

### 改法

判断权收归一个仲裁器，装在**所有 provider 之后**。它只问一件事："这一轮有人产出过东西吗？没有的话，交给 LLM。"

```ts
journal.subscribe(CONTENT_REQUEST, event => {
  if (turnHasContent(journal.read(), request.turnId)) return
  journal.append(LLM_REQUEST, { purpose: 'agent', turnId: request.turnId })
})
```

于是 `content.no_match` 这个事件类型整个删掉，provider 的契约简化成"**命中就产出、不命中就沉默**"，**注册顺序天然成为优先级**，新增 provider 不需要改任何现有插件、也不需要任何中心注册表。

### 真实链路确认：够用，但每个 provider 都得自守卫

这是你特别要求确认的部分。结论分两半。

**能力上够用，而且比信号总线更稳。** 内核对同一事件的订阅者是**串行 await** 的，所以一个异步 provider（比如要走 200ms 网络的小模型）一定会在下一个 provider 之前跑完，也一定在仲裁器之前跑完。仲裁器排在最后，看到的必然是完整结果。这个天然的顺序屏障是内核串行语义免费送的，不需要任何额外机制。

**但成本上有个真实代价：内核会把所有 provider 都跑一遍，哪怕前面已经有人答了。** 正则不命中是免费的，小模型跑一次是 200ms 加真金白银。

所以守卫**不是仲裁器一个人的事——每个 provider 在干重活之前都必须自己问一次**：

```ts
if (turnHasContent(journal.read(), request.turnId)) return
```

这条约束是插件契约，不是内核能替你保证的东西。三条测试把它钉住了：规则命中时分类器一次都没被调用；规则漏掉时分类器能独立答完整轮、全程不惊动 LLM；两个 provider 都弃权时仲裁器只发一次 `llm.request`。

如果将来觉得"每个 provider 自己守卫"太容易忘，还有一条路可选：引入一个 `contentRouter`，先追加 `content.route {provider}`，各 provider 只订阅指向自己的路由（这是 Python 原型 `QueryRouter` + `route.selected` 的做法）。它把决策显式化，但代价是路由器必须知道所有 provider 的身份——回到了你明确不想要的中心化。**现在的方案不需要任何人知道别人存在，我建议先保持。**

### 顺带修掉的

规则匹配用的是 `.map().find()`，急求值，即使第一条已经命中，后面所有规则的 `match` 仍然会跑。正则无害，但一旦规则里有小模型，就变成"每次都把所有小模型跑一遍"。改成 for 循环提前 return。

### 通用规则

**事件的名字必须表达它承载的事实范围。** `content.no_match` 描述的是一个插件的局部结论，却被当成全局结论——名字骗了消费方。局部结论要么不追加事件（沉默），要么名字里带上"谁的"。

## 五、工具状态：我上一份建议是错的

### 现象

mock 工具用闭包变量保存待选联系人：

```ts
let pendingContact: string | undefined
```

同时它又在 `tool.result` 里报告 `state: { key: 'pending.selection', value }`，而运行时上下文插件会把这些 state 折叠出来注入模型上下文。于是待选状态有**两份**，而工具完全不读后者。

### 我上一份文档的建议，以及它为什么错

我当时写的是"让 `execute` 收一份从 Journal 折叠出来的只读 state，工具退化成 `(args, state) => result` 的纯函数"。

**调查真实链路之后，这个建议是错的。**

真实的 Android 链路里，候选列表活在**设备侧的 agent 进程**里：`contact call` 让设备生成并持有一份候选，`select 1` 引用的是**设备那份**。这份状态可以在我们完全不知情的情况下失效——应用重启、会话超时、用户手动干预。

所以真正的责任方**既不是插件，也不是 Journal，而是一个外部会话**。

如果把 Journal 折叠出的 state 喂回工具让它做决策，后果是造出**第二份会静默漂移的设备状态模型**，并且让工具依据"agent 以为的"而不是"设备实际持有的"来行动。这比原来的闭包变量更危险。

### 正确的划分

- **Journal 里的 state 是 agent 的"信念"**，由观测（`tool.result`）累积而来。它用于构建模型上下文，这个用途完全正确；但它**对设备没有权威性**。
- **设备持有"真相"**，agent 无法也不应该镜像它。
- 所以 `execute` 仍然只收参数，不收 Journal state。外部责任方从"藏在闭包里"改成**装配期显式传入的 `AndroidDeviceSession`**，让这条边界在代码里看得见。

### 于是"信念与真相分歧"变成一个正常状况

既然两者必然会漂移，处理分歧就是常规路径而不是异常路径。而它的处理机制——**恰好就是那两条没有测试的错误分支**：工具报告 `no_active_list` 或 `invalid_selection`，`hint` 驱动模型自我纠正。

上一份评审里我把"这两条分支没测试"列为小问题。现在看它其实是核心机制：它是信念/真相分歧的**唯一**处理器。这也正是你在 Q11 批评过的那种情况的反面——不是"做个兜底分支，没有触发，也无法测试验证"，而是一条真实必经的路径。

现在有了完整覆盖，包括一条端到端的场景：第一轮结束时设备还持有候选；两轮之间设备把它丢了；第二轮 Journal 仍然在上下文里宣告 `pending.selection` 存在，模型据此先试 `select 1`，被工具纠正，重新 `contact call`，最终拨通。

### 通用规则

**工具做决策需要的状态，应该放在 `tool.call` 的参数里**——那样模型看得见、Journal 记得住、replay 能重现。工具本身保持"参数 + 外部世界"的纯函数。

**Journal 记录观测，不冒充外部真相。** 分不清这一点，就会造出第二个真相源。

## 六、这一轮对内核的结论

**内核一行没改。** `git diff 7619936 HEAD -- src/journal.ts` 为空。

五个问题里，没有一个的正确解法需要内核提供新能力：

| 问题 | 曾经看起来需要 | 实际用什么解决 |
|---|---|---|
| 并行工具扇出 | barrier / join / correlation | `turnId` + `callId`，插件自己 join |
| 压缩水位线 | 内核 `seq` | 生成的 `requestId` |
| Journal 平方膨胀 | 瞬时 payload 通道 | manifest + 纯投影函数 |
| 内容仲裁 | priority / capability 注册表 | 注册顺序 + 一个末位仲裁器 |
| 工具状态 | 给插件的状态注入面 | 承认责任方在外部，显式传入 |

前四项都在我上一轮列的"演进压力表"里，当时的判断是"先尝试插件方案"。**四次都成立了。** 这比 CASE1 本身跑通更能说明内核的形状是对的。

同时留下一条明确的观察：第二、四节都出现过"我需要知道某个事实在 Journal 里的位置"这个诉求（`events.indexOf`）。目前都用内容标识绕开了。**如果 CASE2、CASE3 继续出现同样的诉求，那就是给内核加 `seq` 的第一个正当理由**——届时它的语义会有三个真实用例来约束。

## 七、还没做的

按上一份评审的排序，以下留给 CASE2：

1. **`src/plugins/*` 与 `src/cases/case1/*` 的重复。** 现在有 5 个同名文件，两个 `llm-openai.ts` 里 fetch 加解析那段是实打实的复制。建议把 `chatCompletion()` 提成零 Journal 知识、零协议知识的纯传输函数，各 case 用自己的协议包成插件；同时决定上一版的 `src/main.ts` + `src/plugins/*` demo 还留不留。
2. **`history.compress.request` 是一跳纯转发。** 把 `instruction` 放进 `history.compaction.required` 就能省掉一个事件类型和一次投递。17 个事件类型对一个 case 偏多，这是最容易砍的一个。
3. **`tsc` 不清理 `dist/`。** 删掉的测试文件会继续参与验证（本轮就撞到过一次，跑出了不存在的第 15 项）。建议 test 前清一次或改用 `tsc --build`。
4. **失控循环没有保护。** 本轮写测试时构造过一个每次都返回工具调用的 provider，结果 Journal 无限增长直到 V8 OOM。这符合 Q02 第 5 点"由业务插件自己保证终止"的约定，但真机上需要有个普通插件来数轮数并追加终止事件。
